# Phase 8: Data Layer - Context

**Gathered:** 2026-05-13
**Status:** Ready for planning

<domain>
## Phase Boundary

Establish the persistence foundation for v2.0: PostgreSQL schema (subscriptions + payment_events tables) with Drizzle ORM, and a Redis singleton via ioredis — both wired and validated in development. No application logic runs against this layer yet; this phase only creates the schema, singletons, migrations, and integration tests. Every downstream phase (9-14) depends on this foundation.

</domain>

<decisions>
## Implementation Decisions

### Local Development Environment
- **D-01:** Reuse the existing Docker Desktop containers from the `clanker_poker` project — both Postgres and Redis are already running. Phase 8 creates a **new database** (e.g., `corretor_unip_dev`) inside the existing Postgres container. No new docker-compose.yml needed.
- **D-02:** Env vars (`DATABASE_URL`, `REDIS_URL`) point to the existing Docker Desktop containers in `.env.local`. A `.env.example` should document the expected format.

### Migration Strategy
- **D-03:** Migrations run via a manual npm script: `npm run db:migrate` (wraps `drizzle-kit migrate`). No auto-migration on app startup -- `instrumentation.ts` is NOT used for migrations. Developers run the command explicitly.
- **D-04:** Migration files are generated by `drizzle-kit generate` and committed to the repo.

### Database Schema
- **D-05:** `subscriptions` table columns: `user_token` (text, primary key), `stripe_customer_id` (text), `stripe_subscription_id` (text), `status` (pgEnum -- see D-06), `expires_at` (timestamp).
- **D-06:** `status` field uses Postgres pgEnum: `pgEnum('subscription_status', ['active', 'cancelled', 'expired', 'onhold'])`. Four values: `active` (paying subscriber), `cancelled` (churned), `expired` (payment lapsed), `onhold` (PIX mandate pending / subscription paused).
- **D-07:** `payment_events` table columns: `stripe_event_id` (text, unique -- idempotency key), `event_type` (text), `payload` (jsonb), `created_at` (timestamp, default now).

### ORM & Driver
- **D-08:** Drizzle ORM with the `postgres` npm package as the driver (not `pg`). Drizzle's recommended driver for Next.js; consistent with STATE.md "postgres driver" notation.
- **D-09:** `lib/db.ts` exports a Drizzle singleton. `lib/redis.ts` exports an ioredis singleton. Both files are new -- no existing pattern to reuse.

### Redis Client
- **D-10:** ioredis (not @upstash/redis). TCP persistent connection to the self-hosted VPS Redis. In dev, connects to the Docker Desktop Redis container.

### Validation
- **D-11:** Phase is considered done when Vitest integration tests pass: a test in `lib/db.test.ts` (or similar) that writes and reads a row from `subscriptions`, and a test that sets/gets a Redis key via the ioredis singleton. These run with the existing `npm test` command (Vitest already configured).
- **D-12:** Integration tests require a live local DB+Redis (Docker Desktop). They should be marked/tagged so they can be excluded from unit-only runs if needed.

</decisions>
